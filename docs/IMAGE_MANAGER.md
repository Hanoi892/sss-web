## 사용 방법

1. 관리자에 로그인합니다.
2. “사이트 반영 위치”에서 페이지와 사진 자리를 선택합니다. 페이지명·업소명으로 검색할 수 있습니다.
3. 사진을 끌어 놓거나 파일 선택 영역을 누릅니다. 휴대폰에서는 사진 보관함·파일 선택을 사용할 수 있습니다.
4. 제목과 ALT를 확인합니다. 기본값은 파일명에서 자동으로 채웁니다.
5. “선택한 사진 업로드”를 누릅니다. 최대 30장을 선택하고, 동시에 두 장씩 처리합니다.
6. 각 사진의 원본 전송률과 압축·검증 상태를 확인합니다.
7. 완료된 사진은 지정한 위치에 반영됩니다. 공개를 해제한 사진은 관리자만 볼 수 있습니다.
8. 등록 사진의 미리보기·수정·교체·삭제 버튼을 사용합니다. 순서는 카드 드래그 또는 위/아래 버튼으로 바꿉니다.

같은 위치에 여러 사진을 지정하면 순서대로 보여주는 이전/다음 버튼이 표시됩니다. 사진을 교체하면 같은 DB ID를 유지하면서 파일 URL 버전이 갱신됩니다. 페이지를 새로 열거나 다시 포커스하면 갱신하고, 열린 페이지도 60초마다 변경을 확인합니다.

## 압축·검증

- 입력: JPG/JPEG, PNG, WebP, AVIF, 서버 디코더에서 지원되는 HEIC/HEIF.
- 장당 50MiB, 6,400만 화소 상한. 애니메이션과 다중 이미지 파일은 거부합니다.
- 확장자뿐 아니라 실제 시그니처와 디코더 결과를 검증합니다.
- EXIF 회전을 적용하고 sRGB로 색상을 변환합니다. 투명도를 유지하고 위치정보 등의 EXIF는 제거합니다.
- 원본 해상도에서 WebP 품질 45~92를 이진 탐색합니다.
- 원본 해상도의 WebP가 품질 하한에서 맞지 않으면 AVIF를 시도합니다.
- 두 형식 모두 300KB를 넘을 때만 너비를 단계적으로 12%씩 줄입니다. 원본 비율을 유지합니다.
- 각 해상도에서 품질 하한 이상으로 조건을 만족하는 가장 높은 탐색 품질을 선택합니다. 이는 주관적 화질을 측정하는 절대 최적해가 아니라, 해상도와 품질 하한을 우선하는 제한된 탐색 방식입니다.
- 메모리의 최종 파일과 영구 저장소에서 다시 읽은 파일을 각각 검증합니다. 최종 파일이 307,200바이트 이하이고 SHA-256이 일치해야 DB에 등록합니다.
- 실패한 원본은 공개하지 않습니다. 원본과 실패한 결과는 정리하고 오류를 표시합니다.
- HEIC는 런타임의 HEVC 디코더 지원에 따라 실패할 수 있으며, 실패 시 JPG로 내보내 다시 올리도록 안내합니다.

## 영구 저장소 및 DB

기존 Supabase를 재사용합니다. 배포 런타임의 로컬 디스크에 이미지를 저장하지 않습니다.

- 비공개 Storage 버킷 `dbj-image-incoming`: 서명된 URL로 원본 직접 업로드, 장당 50MiB.
- 비공개 Storage 버킷 `dbj-image-optimized`: 검증 완료 결과만 저장, 장당 307,200바이트.
- 기존 PostgreSQL 안에 별도 `image_manager` 스키마를 생성합니다.
- 관리자, 세션, 요청 제한, 업로드 작업, 이미지 메타데이터를 이 스키마에만 저장합니다.
- 스키마의 PUBLIC 접근 권한을 회수하고 서비스 측 자격증명으로만 조회합니다.
- 기존 테이블·버킷을 수정하거나 비우지 않습니다.
- `api/image-file`은 공개 상태 또는 관리자 세션을 확인한 뒤 파일을 제공합니다. 저장소 원본 URL은 공개 API로 반환하지 않습니다.
- 이미지 URL: `/api/image-file?id=<UUID>&v=<버전>`.
- 공개 이미지는 private/no-cache + ETag로 재검증하고, 비공개 이미지는 no-store를 적용합니다. 공개 취소 시 URL 직접 접근도 차단합니다.
- 교체 성공 후 이전 관리 이미지 파일을 정리합니다. 삭제는 이 시스템에서 등록한 사진에만 적용됩니다.
- 처리 중인 원본은 완료·실패 시 삭제하며, 2시간이 지난 중단 업로드는 다음 업로드 준비 시 정리합니다.

필요한 기존 서버 환경변수:

```
POSTGRES_URL (또는 POSTGRES_PRISMA_URL)
SUPABASE_URL (또는 NEXT_PUBLIC_SUPABASE_URL)
SUPABASE_SERVICE_ROLE_KEY (또는 SUPABASE_SECRET_KEY)
IMAGE_ADMIN_SETUP_TOKEN
```

환경변수는 프런트엔드 번들에 삽입하지 않습니다. DB 역할에 새 스키마 생성 권한과 Supabase 서비스 역할에 새 비공개 버킷 생성 권한이 있어야 합니다.

### 2026-11-18 DB 인증서 연결 오류 수정

검증 배포의 `/api/image-auth` 로그에서 `SELF_SIGNED_CERT_IN_CHAIN`을 확인했습니다.
Supabase PostgreSQL CA가 기본 Node 신뢰 목록에 없어 최초 상태 조회가 실패한 문제입니다.

- Supabase 루트 CA를 서버 번들에 포함하고 인증서 체인·호스트 이름 검증을 유지합니다.
- node-postgres가 URL의 `sslmode` 때문에 명시한 CA를 덮어쓰지 않도록 Supabase 연결 옵션을 정규화합니다.
- 인증서 검증을 비활성화하는 옵션은 사용하지 않습니다.
- Vercel 빌드에서 실제 DB의 TLS 검증과 `SELECT 1`, 관리자 상태 핸들러를 검사합니다. 이 검사가 실패하면 배포 빌드를 중단합니다.
- 인증서·연결 설정 회귀 테스트 4개와 기존 API·보안 테스트를 합한 관련 테스트 26개가 통과했습니다.

CA 배포 위치: https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt
SHA-256: `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`
유효 기간: 2021-04-28 ~ 2031-04-26.

수정 배포 빌드의 실제 환경 검증 결과:
- TLS 인증서 체인·호스트 이름 검증과 `SELECT 1` 성공.
- 관리자 상태 핸들러 200 응답, 최초 계정 설정 필요 상태 확인.
- 기존 Supabase에서 비공개 원본 서명 업로드 → 압축 → 결과 저장 → 저장 바이트·해시 재검증 성공(테스트 이미지 806바이트).
- 생성한 테스트 파일은 검증 직후 정리했습니다.
- 실제 사용자의 브라우저 로그인·대용량 업로드·모바일 조작 검증은 별도입니다.

### 업소별 사진함
관리자 업로드 대상을 동밤정 지역별 업소 목록에 표시되는 31개 업소별 사진함으로 바꿨습니다. 업소를 선택하고 대표 사진 1장 또는 추가 사진 여러 장을 선택합니다. 대표 사진은 해당 업소 상세 대표 영역과 목록·관련 업소 카드에 자동 연결하고, 추가 사진은 해당 업소 상세의 사진 모음에 표시합니다. 기존 영역별 사진 기록은 유지합니다. 표시 비율은 4:3이며 원본은 자르지 않고 contain으로 보여줍니다. 파일 자체 해상도는 압축 엔진이 우선 보존하고, 결과는 307,199바이트 이하입니다. 관련 API·보안 테스트 23개 통과 및 정적 빌드 성공.

### 실제 파일 규격 통일
최신 사용자 요청에 따라 출력 파일을 모두 1280×960px로 통일합니다. 원본 비율은 유지하고 남는 공간을 여백으로 채우며, 투명 이미지의 투명도를 보존합니다. 고정 해상도에서 품질을 탐색하고 307,199바이트 이하만 저장합니다. 기존 등록 파일도 같은 엔진으로 변환하여 저장 파일의 해시·용량·해상도를 검증한 뒤 DB 연결과 캐시 버전을 갱신합니다. 이전 객체는 복구용으로 남겨두며 기존 제목·ALT·업소·순서·공개 상태는 유지합니다. 이전 원본 해상도 우선 규칙보다 이 고정 규격 요청을 우선합니다.

### 여백 없는 사진 규격
사진이 실제로 동일하게 보이도록 contain 여백 방식을 폐기하고 중앙 crop/cover로 1280×960px를 꽉 채웁니다. 기존 검은 여백은 trim 처리한 후 재변환합니다. 세로 사진의 위아래 등 가장자리 일부가 잘릴 수 있습니다. DB fit_version으로 기존 파일도 한 번 재처리하며, 300KB 미만·해시를 검증하고 연결 버전을 갱신합니다.

### 최신 운영 콘텐츠와 동기화
오래된 관리자 브랜치를 최신 main의 콘텐츠와 병합했습니다. 하노이 가라오케 8곳, 나트랑 마사지 12곳을 포함해 현재 지역별 목록에 표시되는 62곳을 관리자에 반영합니다. 최신 HTML·검색·사이트맵·관련 업소 스크립트를 보존하고 문의 스크립트에는 최신 관련 카드 로더와 이미지 로더를 모두 유지합니다. 기존 등록 사진의 DB 레코드·업소 연결·파일은 삭제하지 않습니다.

### 관리자 업로드 횟수 제한 제거
사진 100장 이상을 올릴 때 차단되던 시간당 업로드 준비 요청 100회 제한을 제거했습니다. 이미 인증된 관리자의 업로드 준비에는 횟수 제한을 적용하지 않습니다. 파일 크기·형식·픽셀 수·최종 용량 검증과 관리자 권한 확인은 유지합니다. 로그인 시도 제한은 그대로입니다. 105회 연속 업로드 준비가 성공하는 API 회귀 테스트를 추가했습니다.

### 관련 업소 카드 대표 사진 연결
related.js가 처음 로드된 카드를 나중에 교체하는 경우도 MutationObserver로 감지합니다. 매번 현재 카드 DOM을 다시 확인하고 업소 링크의 정규화된 경로로 대표 사진을 연결합니다. 카드 개수가 같거나 이미지 API 응답이 같아도 교체된 카드에는 사진과 ALT를 다시 적용합니다. 동명이거나 다른 업소에는 사진을 섞지 않습니다. 해당 동작을 실제 image-manager.js 실행 단위 테스트로 검증했습니다.

### 상세 본문 사진 배치와 공개 문구 정리
62개 업소의 대표 사진은 유지하고, 추가 사진은 각 상세 본문의 주요 안내 구간에 나누어 표시합니다. FAQ·관련 업소 안내 앞의 본문 구간을 사용하고 사진 수가 늘어도 빠뜨리지 않습니다. 실제 사진 내용이 확인되지 않은 상태에서 시설 종류를 단정하지 않으며, 이미 작성한 구체적인 ALT는 유지합니다. 파일명 그대로인 ALT는 업소명·사진 구분에 맞게 정리합니다. 기존 파일·업소·공개 상태·사진 순서는 바꾸지 않습니다.

공개 HTML은 빌드 시 scripts/public-copy.cjs를 통해 방문자용 문구로 변환합니다. ‘상세 허브’, ‘업소 카드’, ‘메인글’, ‘상세글’, ‘ALT 입력 예정’ 등은 공개 출력에 남지 않게 검사하며, 링크·스크립트·본문의 사실 정보는 유지합니다. 관리자 화면은 이 정리 대상에서 제외합니다.

### 본문 사진을 작게 표시하고 클릭 확대
본문 사진은 최대 폭 400px(모바일 340px)로 줄여 글 사이에 배치하고, 대표 사진도 최대 560px로 제한합니다. 사진을 누르면 접근 가능한 dialog로 확대하며 닫기 버튼·Escape·배경 클릭으로 닫습니다. 원본 비율과 저장 규격은 그대로이며, 이미지 위의 작은 ‘크게 보기’ 안내 외에 불필요한 박스나 장식은 추가하지 않습니다. 일반적인 자동 사진 번호 캡션은 숨기고 ALT는 유지합니다.
